# Local OCR and the extraction port split — archived 2026-08-09

Set aside on 2026-08-09. None of this work is in this repository — the code was preserved on a
development branch that is not published here. This document is the summary that stays behind
so the work is findable without it, and it is detailed enough to rebuild from.

Read alongside [DESIGN.md](./DESIGN.md) §12, which has called Hebrew extraction quality "the
single biggest determinant of whether the app is pleasant or annoying" since before there was
an app.

---

## The question

Can OCR and field extraction stop sending medical documents to a third party?

The trade was undecidable because nobody had a number. So this pass built the thing that
produces the number — a benchmark that scores engines field-by-field over the same documents
— and a local engine to point it at.

## What was built

The pass split one port into two and added three engines behind them.

`extractFromDocument` left `LlmPort` for a new `ports/ocr.ts`, which separates:

| port | job | who can do it |
|---|---|---|
| `OcrPort` | pixels → text | Tesseract, a vision model, Claude |
| `ExtractionPort` | a document → the fields the app stores | needs judgment: which of three dates on a discharge letter is *the* date |

`LlmPort` kept `complete` for M4/M5. `ClaudeAdapter` implemented both and behaved exactly as
before; `getExtraction()` in the container was the one line that chose, on `EXTRACTION_ENGINE`.
The prompt and schema moved to `documents/internal/extraction-spec.ts` so the benchmark
measured the pipeline the app actually runs rather than a copy that drifts.

**Files, ~2,200 lines:**

Dependencies added: `tesseract.js`, `pdfjs-dist`, `@napi-rs/canvas`.

### The pipeline is a ladder, and the first rung does most of the work

| rung | when | cost |
|---|---|---|
| PDF text layer | PDF has usable, decodable text | ~10 ms, exact |
| rasterise 300 DPI → OCR | scanned PDF | ~10–30 s/document |
| OCR | photograph | ~5 s/document |

Six of the eight real PDFs already carried a text layer — generated by a portal or a hospital
system, never printed. **The text layer is more accurate *and* twice as fast**, which is what
made the local option viable at all: with the ladder, 89% mean over 85 s; forcing OCR on
everything, 85% over 181 s.

## What was measured

### Synthetic Hebrew, 2026-08-06 — the ceiling

Rendered Hebrew, then degraded deliberately. Word recall against the source text:

| condition | recall | Tesseract's own confidence |
|---|---|---|
| clean render, 1000px | 100% | 91 |
| clean render, 400px | 73% | 81 |
| JPEG quality 15 | 100% | 91 |
| sensor noise, amplitude 100 | 100% | 91 |
| skew 3° | 93% | 84 |
| skew 7° | 87% | 79 |
| **skew 3° + noise 50** | **40%** | **90** |
| skew 3° + noise 50 + JPEG 40 | 37% | 88 |

1. **The `heb` model is not the weak part.** Clean Hebrew reads perfectly. Compression is a
   non-issue and so is noise. Individually, so is mild skew.
2. **Skew and noise together collapse it** — precisely what a phone photo of a letter lying on
   a table is. Neither Otsu binarisation, box-blur denoising, nor un-rotating by the exact
   known angle recovered any of it: 40% stayed 40%. The oracle deskew is confounded (undoing a
   rotation resamples a second time, damaging about as much as it repairs), so this says the
   damage is not trivially reversible, not that skew correction is worthless.
3. **Confidence did not track accuracy** — 88–92 reported while recall was 37–40%.

### Nine real records, 2026-08-07 — the answer

Nine genuine documents (a named person's oncology history, in gitignored `test_files/`), with
`documents.extracted_text` supplying a reference for each.

**Result: 89% mean token recall against Claude's text, worst document 76%, 9/9 read, 85 seconds
for nine documents. Nothing left the process.**

**What the reference is worth:** it is what Claude read, not what the documents say. One row
makes the point — `אישור זכאות לקצבת שירותים מיוחדים – ביטוח לאומי`, a 13-page National
Insurance bundle, is a document where **Claude extracted zero characters** and the local
pipeline extracted 1,391 tokens. It was reported `n/a` rather than averaged in, because scoring
it would blame the local pipeline for the model's failure.

### Three bugs found only by running it on real documents

1. **A PDF text layer that decodes to glyph indices.** One hospital referral embeds a subset
   font with a broken `ToUnicode` map, so pdfjs returned every Hebrew letter shifted 0x330 into
   the IPA block — `ʤʮʥʹʸʤ` for `הרשומה`. Its *Latin* runs decoded perfectly, so it scored 100%
   precision while carrying no Hebrew: a silent, confident, near-total loss. `looksLikeRealText`
   was taught to reject such a layer and rasterise instead. That document went **21% → 77%**.
   Un-shifting was rejected as a fix — the offset belongs to one font subset, not to a standard.
2. **Hebrew-only OCR on an English document.** An oncology summary written entirely in English
   came back as 537 confident Hebrew tokens of which 5% were right; `Diagnosis:` became
   `818סתפ18כ1`. Loading `heb+eng` and deciding per word took that document **5% → 96%** and the
   whole suite **75% → 89%**.
3. **Empty references corrupt the pairing.** The zero-character row could not compete on content,
   so greedy assignment handed it a leftover file — and the file it took belonged to a row that
   then settled for an unrelated 13-page bundle. One bad row corrupted two. Empty references were
   held back and assigned by elimination, and filename similarity added as a second signal
   because it survives exactly the documents OCR fails on.

### On Tesseract's confidence score

The two passes disagreed and both stand. On real documents it tracked well — the English
document read at confidence 33 while failing, and 92 once `eng` was loaded. On synthetic it
reported 90 on garbage. **Low confidence appears to mean something; high confidence does not.**
Treat it as a usable alarm and never as a warrant. `ports/ocr.ts` recorded it and refused to act
on it.

### The comparison that never completed

`verify:ocr` ran any of three engines over the same documents as columns:

| engine | 2026-08-07 result |
|---|---|
| `local` | 89% whole pipeline (8 documents), 87% engine only (4), worst 76%, 9/9 read, 50 s |
| `vlm` | **not run** — no endpoint configured |
| `claude` | **not measurable** — the API key had no credit balance. It failed on all four documents that actually needed reading; its apparent 92% was over four text-layer rows it never touched |

Two means were reported deliberately: *whole pipeline* is what a user would get, *engine only*
drops the text-layer rows and is the only column-to-column comparison worth anything, since
those rows are identical code in every column. Both printed the count they covered — without
it, an engine that failed on five documents and scored well on four easy ones reports a better
average than one that read all nine.

## Known limits, at the point of archiving

- **Tesseract alone cannot read PDFs.** It takes rasters. The ladder worked around this; the
  bare adapter raised `UnreadableDocumentError` rather than returning an empty extraction.
- **`actionSummary` was quoted from the document, never composed**, and `name` was assembled
  from recognised parts rather than taken from the OCR's first line — which on a letterhead is
  a logo misread as gibberish. Everything the heuristics could not determine came back `null`,
  because a wrong hospital on a medical record is believed and a blank one gets filled in.
- **The 76% floor is a floor on *agreement*, not on correctness.** Nobody read the local output
  beside the document to see which of the two is right where they differ. This is the largest
  thing left unanswered.
- **`vendor/tessdata` was pinned** via `TESSDATA_PATH` because tesseract.js otherwise fetches
  from a public CDN on first use — which would have the local engine calling a third party on
  every cold start, defeating its only purpose.

## The larger point, unresolved

Removing Anthropic from extraction narrows the trust boundary by one party. **It does not close
it.** The files are in Google Drive and `extractedText` — the full OCR of every record — is in
hosted Postgres. If the goal is that no health data reaches a third party, extraction is the
smallest of the three problems, and the other two are storage decisions rather than OCR ones.

This is the sentence to start from if the question is ever reopened.

## How to revive it

```bash
git checkout archive/local-ocr-extraction
npm install                    # tesseract.js, pdfjs-dist, @napi-rs/canvas
npm run verify:fields          # 27 checks, no database, no network — proves the tree is sound
```

The branch is self-contained, `vendor/tessdata` included. To run the real-document benchmark
you also need `test_files/` with the documents and a database holding their
`documents.extracted_text` — neither is in version control and neither ever should be, since
both are health data.

`EXTRACTION_ENGINE=local` was the switch; unset meant Claude, which is what `main` does
unconditionally again.

Two cautions before trusting it in the app rather than in a script:

- **The local engine was only ever run through `tsx` scripts, never through a request.**
  `npm run build` passed and the benchmark ran end to end, but no document was ever scanned by
  the local engine via `extractFromScan` on a running server. `tesseract.js` (a WASM worker),
  `pdfjs-dist` and `@napi-rs/canvas` (a native binding) are exactly the kind of dependency that
  works under `tsx` and then needs `serverExternalPackages` in `next.config.ts` — which the
  archived branch never added, because nothing forced the issue.
- **A Tesseract worker holds the Node event loop open.** `OcrPort.close()` exists for that
  reason and the scripts call it. On a server the liveness between requests is wanted; on
  Vercel's per-invocation model it is a question nobody asked.
